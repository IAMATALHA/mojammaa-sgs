# App audit — 28 September 2026

The app passes its existing automated checks, but the audit and follow-up reproduced **eleven weaknesses: four P1 and seven P2**. The initial pass found F1–F9; a requested follow-up confirmed F10–F11 with the real attendance functions against a local Firestore emulator. The newest phone-login flow has a school-wide denial-of-service weakness and the country field corrupts middle edits. Older gaps remain in file access, permission revocation, attachment validation, resource ownership, offline logout, and attendance. Passing the current suite does not cover these cases.

P1 means prioritize before the next release; P2 means a concrete defect to address in the next maintenance batch. These are remediation priorities, not CVSS scores. No production attack was attempted and no school records were retrieved.

**Scope and baseline.** Mobile repository: `f5b919b`, clean at audit start, Expo 54.0.37 / React Native 0.81.5 / app 1.0.17. Review began with `bbb3751..f5b919b`, then covered the September 27 security/homework changes and the app's central authorization, session, data, notification, and release paths. Phone authentication lives in the adjacent `mojammaa-admin` repository; its relevant source at `65ac82f` was read and exercised with injected synthetic dependencies. Its unrelated working-tree changes were left alone. Deployed function binaries were not compared with source.

**F1 — P1 — Anonymous phone attempts can block login for every family. New phone-login backend.**

Source: [parentPhoneLogin.ts](/Users/atalhayoussef/mojammaa-admin/functions/src/parentPhoneLogin.ts:185), limits at [line 32](/Users/atalhayoussef/mojammaa-admin/functions/src/parentPhoneLogin.ts:32), public callable at [index.ts:439](/Users/atalhayoussef/mojammaa-admin/functions/src/index.ts:439).

Every syntactically valid attempt consumes the shared 300/minute and 3,000/day counters **before** checking whether the phone exists. No caller-specific quota or App Check requirement is present in this handler. Rotating through unknown numbers defeats the per-phone cap while consuming the entire school's budget.

Proof: executed the actual verifier with an in-memory Firestore double, default limits, and fake Auth/password services. A legitimate parent succeeds initially. Then 3,000 unknown-phone attempts, spread over ten minute windows, consume the day budget. After the minute window expires, the same legitimate parent is rejected with `too-many-attempts/global-cap` before password verification. Existing authenticated sessions and email login are not affected. No live requests were sent.

Remediation: isolate abusive callers before consuming a shared budget; preserve per-account limits and enumeration-resistant responses. Design a recovery/challenge path that does not let arbitrary unknown numbers exhaust all legitimate login capacity. App Check can add a barrier, but needs a compatible client rollout and is not a replacement for quota design. [Firebase documents callable App Check enforcement](https://firebase.google.com/docs/app-check/cloud-functions).

Acceptance: unknown-phone flooding must not prevent a previously untouched legitimate account from logging in, while password guessing against a victim remains limited.

**F2 — P2 — Editing a formatting space deletes the wrong phone digit. New in `cfe13f1`.**

Source: [PhoneNumberField.tsx:89](../src/components/PhoneNumberField.tsx#L89).

The deletion heuristic always uses `digits.slice(0, -1)`, regardless of cursor position. With `06 12 34 56 78`, deleting the first space produces the input event `0612 34 56 78`; the handler stores `061234567`, deleting the final `8`. This can corrupt activation/login identifiers while the user is correcting an earlier part of the number.

Proof: extracted and executed the actual `onChangeText` arrow from the TSX source with synthetic state. The existing utility tests cover formatting and pasting, but do not exercise this handler.

Remediation: preserve digits when only separators change, or implement selection-aware deletion and cursor preservation. Test backspace, selection replacement, paste, and edits in the middle on Android/iOS.

**F3 — P1 — Storage bypasses the newly enforced teacher/class isolation. Existing rules, newly relevant to September 27 restriction.**

Source: [storage.rules:29](../storage.rules#L29), [storage.rules:69](../storage.rules#L69), contrasting [firestore.rules:553](../firestore.rules#L553).

Homework and resource objects allow `read` to every authenticated account. A teacher denied another teacher's homework document can still download its attachments. An unrelated parent can list the teacher's homework folder. Knowing an author UID is sufficient to discover filenames; this does not require guessing a complete attachment URL. The corresponding write checks also do not require a teacher role, only a matching UID and allowed file type.

Proof: local emulator denied the other teacher's homework document read, allowed that teacher's file download, allowed an unrelated parent's folder listing, and denied an anonymous SDK file download. These rules match production. Firebase's `read` permission includes both `get` and `list`. [Storage rule operation reference](https://firebase.google.com/docs/storage/security/core-syntax#granular_operations).

Remediation: associate each object with a homework/resource identity and validate the intended teacher/admin/current-guardian audience. Separate listing from download permissions and prevent broad folder enumeration. Migrate existing objects/clients before closing compatibility paths; a blanket denial would break legitimate family downloads.

Acceptance: owning teacher, relevant family and admin succeed; unrelated parent, colleague and anonymous caller fail, for both listing and download.

**F4 — P1 — Concurrent guardian rebuilds can restore revoked class access. Existing backend.**

Source: [guardianAccess.js:18](../functions/guardianAccess.js#L18), [guardianAccess.js:35](../functions/guardianAccess.js#L35), trigger at [index.js:403](../functions/index.js#L403).

The authoritative child query and the derived `guardianAccess` write are separate operations. One invocation can read the old relationship, a newer invocation can remove access, and the older invocation can then overwrite that revocation with its stale result. Class-scoped rules trust this derived document. The resulting stale capability can persist until another relevant event or backfill rebuilds it.

Proof: executed the actual rebuild function against a controlled asynchronous database double. Paused the old invocation immediately before its write; removed all children; completed the newer deletion; resumed the old write. The revoked class reappeared. This proves the interleaving, not that it has occurred in production. Firebase does not guarantee trigger ordering and can deliver events more than once. [Firestore trigger limitations](https://firebase.google.com/docs/functions/firestore-events#limitations).

Remediation: recompute and commit against transactionally checked current state, or serialize/version rebuilds per guardian so stale work cannot overwrite newer state. Add retry/reconciliation for failures. Direct student/grade reads still use the live child relationship; the demonstrated exposure is the class capability, not unrestricted student-record access.

Acceptance: overlapping link, unlink, archive, and transfer events always leave the capability equal to current authoritative relationships.

**F5 — P1 — A parent can submit an attachment that crashes the admin message view. Existing, acknowledged but unfinished in release notes.**

Source: message creation at [firestore.rules:743](../firestore.rules#L743), rendering at [AdminMessagesScreen.tsx:305](../src/screens/admin/AdminMessagesScreen.tsx#L305). The same unchecked pattern exists in teacher/parent message screens and [useParentMessages.ts:32](../src/hooks/useParentMessages.ts#L32).

Message rules do not validate attachment shape. A valid parent-to-admin message can include `attachments: [{ url: 'https://example.invalid/a', name: 'a', mime: 42 }]`. Optional chaining on `mime` only handles null/undefined; calling `startsWith` on a number throws. Parent home conversion also uses this pattern for received messages, broadening the impact of malformed staff content.

Proof: emulator accepted the synthetic parent's write and the admin's read; executing the current renderer expression on that document raised `TypeError`. A native process crash was not tested; the confirmed failure is an uncaught render-path exception.

Remediation: apply `safeAttachments` at every message/resource read boundary, validate writes server-side/in rules within rule expression budgets, and handle invalid historical records. This should not be limited to the homework path already fixed.

Acceptance: malformed arrays, null entries, numeric MIME, object names and invalid URLs cannot crash inbox/detail/home screens. Legitimate attachments still render.

**F6 — P2 — Resource updates bypass class scope and teacher ownership checks. Existing rules.**

Source: [firestore.rules:670](../firestore.rules#L670).

The create rule requires the author's assigned class and own `teacherId`. The update rule checks only the old owner and append-only `viewedBy`; the owner can change `classeId` to another class and `teacherId` to another teacher. This publishes content outside the teacher's assigned audience and corrupts ownership attribution.

Proof: direct creation in an unassigned class was refused; updating an owned resource to that class and the other teacher's ID succeeded in the emulator.

Remediation: keep author identity immutable for non-admins and validate the old/new class scope on every content update. Preserve a separately authorized view-receipt path.

**F7 — P2 — Parent homework proofs accept arbitrary external URLs. Existing rules.**

Source: [firestore.rules:125](../firestore.rules#L125), [HomeworkTeacherTracking.tsx:251](../src/components/homework/HomeworkTeacherTracking.tsx#L251), [attachments.ts](../src/utils/attachments.ts).

Proof validation checks only list length, comment and timestamps. It does not require uploaded objects, the correct Storage bucket, or matching homework/child/parent metadata. `safeAttachments` filters types but accepts any string URL. Teacher review renders `image/*` URLs directly and opens attachment URLs on press. A forged proof can therefore load content from an attacker-controlled host or present a deceptive link, and arbitrary URLs qualify as submitted evidence.

Proof: emulator accepted a parent's submission with an external `https://example.invalid/untrusted.jpg` attachment. No external host was contacted. Other users' private-object access was not demonstrated by this case.

Remediation: validate Storage object identity, ownership and linkage to the submission; allow only supported schemes and trusted origins at the read boundary as defense in depth. Keep the five-attachment limit.

**F8 — P2 — Unlinking a guardian does not revoke reads of existing proof objects. Existing Storage rules.**

Source: [storage.rules:52](../storage.rules#L52), URL creation at [StorageService.ts:74](../src/services/StorageService.ts#L74).

The parent read branch trusts the uploader UID embedded in the path/metadata, without rechecking the current `eleves.parentUid`. Removing the child relationship revokes the student document but not fresh SDK downloads of those existing proof files. This concerns previously uploaded evidence, not new uploads under a replacement parent's account. Download-token URLs also require a separate revocation design; changing rules alone is not proof that previously distributed links are revoked.

Proof: unrelated parent was denied the proof object. After an Admin-SDK fixture change transferred the child, the old parent was denied the student document but could still download the original proof object. This was a fresh emulator read, not a device cache.

Remediation: define the intended historical-access policy explicitly. If unlink/offboarding revokes access, check live guardianship at read time and use a delivery/token strategy consistent with revocation. Test both SDK access and existing download links.

**F9 — P2 — A push-service/network failure prevents local logout. Existing session flow.**

Source: [AuthContext.tsx:179](../src/contexts/AuthContext.tsx#L179), [NotificationService.ts:93](../src/services/NotificationService.ts#L93).

`logout()` waits for remote push unregistration and calls `signOut` only after success. Offline or function failures leave the user signed in on the device. Settings reports an error, but cannot actually end the session. This makes a privacy-sensitive action depend on an unrelated service being available.

Proof: extracted the real logout callback and injected a rejecting push-unregister function. `signOut` was never invoked.

Remediation: separate local session termination from push-delivery cleanup while preserving the existing account-switch privacy guarantee. Design durable cleanup/reconciliation, locally suppress stale-account notification content, and test delayed requests and account switches. Merely swallowing the unregister failure would risk exposing old-account pushes to the next user.

**F10 — P2 — Attendance can be recorded on a cancelled school day. Follow-up finding.**

Source: [attendanceSubmission.js:25](../functions/attendanceSubmission.js#L25), validation at [line 8](../functions/attendanceSubmission.js#L8). The teacher action dashboard checks `joursScolaires.annuleCours`, but attendance loading/submission does not consult the school calendar. The class-folder attendance path also resolves the weekly schedule without that calendar gate.

Proof: seeded a synthetic Monday weekly lesson and `joursScolaires/2026-09-28` with `annuleCours: true`. Both `loadAttendance` and `submitAttendance` succeeded, creating an absent record. A teacher from an unrelated class was refused as a negative control. The persisted false absence can affect attendance statistics and enter the usual school-alert path; no push notification was actually sent in this test.

Remediation: enforce calendar cancellations in the authoritative load/submit paths, including rechecking within submission transactions for queued offline work. Define any admin override explicitly. Acceptance: a normal scheduled day succeeds; a cancelled day is rejected without attendance writes, including when cancellation happens after a draft was prepared.

**F11 — P2 — Rejected absence declarations leave an old justification active. Follow-up finding.**

Source: [attendanceSubmission.js:81](../functions/attendanceSubmission.js#L81), merge write at [line 84](../functions/attendanceSubmission.js#L84). Justification fields are written only when a matching accepted/pending declaration exists. When that condition stops being true, the merge keeps the previous `justified: true` and `raison` values.

Proof: submitted an absence with a pending synthetic declaration; the function approved it and marked the absence justified. Changed the declaration to `declined`, then resubmitted with the correct latest attendance version. The absent record still had `justified: true` and its old reason. Changing the status to present also retained those fields. These were actual function calls against the local emulator.

Impact: the parent absence screen labels the record as justified and `getDashboardActions` omits it from unjustified-absence counts even after the declaration was rejected. Remediation: explicitly reconcile or clear justification fields when a declaration is rejected or ceases to apply; distinguish any independent staff justification if supported. Acceptance: pending/approved declarations justify absences, rejected declarations do not preserve stale automatic justification, and present/late corrections have consistent metadata.

**Additional activation issues identified by code tracing; native reproduction still pending**

1. [ParentActivationScreen.tsx:70](../src/screens/auth/ParentActivationScreen.tsx#L70) signs into the existing account before awaiting `linkParentInvitation`. [NavigationRoot.tsx:120](../src/navigation/NavigationRoot.tsx#L120) replaces the auth screen on auth/profile changes. If linking is slow and then fails, `setError` targets a screen already removed; the parent reaches the dashboard without the new child or visible recovery. This sequencing predates phone login, and now also applies to its phone collision branch. Keep linking progress/error state outside the disappearing screen or finish it in an authenticated linking flow. Test success and forced failure with a delayed callable.
2. In [admin index.ts:310](/Users/atalhayoussef/mojammaa-admin/functions/src/index.ts:310), an email-based activation retries without phone login when the phone is already claimed or invalid in Auth. It returns `loginPhone: null`; the mobile success branch only explains the login identifier when a phone exists. A user can confirm a phone and enter the app without being told that only email login was enabled. Show an explicit email-only result and remember the usable login mode. This is an onboarding/recovery gap, not an authentication bypass.
